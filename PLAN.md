# Interviewer's Little Helper — план архитектуры MVP

Статус: **на согласовании, код не пишется до подтверждения плана.**
Спорные места помечены ⚠️, открытые вопросы — в разделе 9 (у каждого есть дефолт, чтобы работа не блокировалась).

## 1. Сводка решений

| Компонент | Выбор | Почему |
|---|---|---|
| ASR, macOS | `mlx-whisper` + `whisper-large-v3-turbo` | Metal-ускорение на Apple Silicon, мультиязычность RU/EN |
| ASR, Windows | `faster-whisper` (CTranslate2, CUDA) + `large-v3-turbo` | Лучшая скорость/VRAM на NVIDIA |
| ASR, CPU-фолбэк | `faster-whisper` int8 | Работает на обеих ОС |
| Сегментация речи | Silero VAD (ONNX, CPU) | Режем чанки по паузам, не по таймеру; ~1 МБ, без torch |
| Захват аудио | `sounddevice` (PortAudio) | Кросс-платформенный, перечисление устройств, callback → кольцевой буфер |
| LLM-сервер | **Ollama** (localhost HTTP) | Единый API на Mac/Win, structured outputs (`format` = JSON-схема), keep_alive |
| LLM-модель | **Qwen3-8B Q4_K_M** на обеих платформах ⚠️ (не 14B — обоснование в §3) | Сильный русский, надёжный JSON, влезает рядом с Whisper в 12 GB |
| Бэкенд | FastAPI + uvicorn + WebSocket | По ТЗ |
| Фронтенд | Один статический HTML/CSS/JS без сборки и без CDN | Приватность (ноль внешних запросов), простота |
| Окно | `pywebview`: нативное окно 600×400, `on_top=True` | Висит поверх Zoom; фолбэк `--browser` без always-on-top |
| Валидация схем | `pydantic` | Схемы гайда/покрытия/ответа LLM + устойчивый парсинг |

Всё локально: сервер слушает только `127.0.0.1`, фронт не тянет ни одного внешнего ресурса, телеметрии нет. Сеть нужна один раз — скачать веса моделей при установке (данные интервью в этом не участвуют).

## 2. Почему такие модели

### ASR: `large-v3-turbo`
- 809M параметров, ~1.6 GB FP16 / ~1 GB int8 — на порядок быстрее `large-v3` (4 слоя декодера вместо 32) при почти том же качестве мультиязычного распознавания. RU и EN — из сильных языков Whisper.
- Язык **не фиксируем**: автоопределение на каждый чанк. Whisper выбирает один язык на окно ~30 с, поэтому переключение внутри фразы даст шум на стыке ⚠️ — по ТЗ это приемлемо. Нарезка по паузам смягчает проблему (реплики чаще одноязычны).
- Один экземпляр модели на оба канала (очередь), а не два — экономим VRAM.

### LLM: Qwen3-8B Q4_K_M (дефолт), Qwen3-14B — опция
- Требования: уверенный русский, строгий JSON, редкие короткие всплески раз в 4 минуты. Семейство Qwen — один из лучших открытых вариантов по русскому; Qwen3 в Ollama ставится одной командой (`ollama pull qwen3:8b`), режим размышлений отключаем (`think: false`) — для JSON-классификации он не нужен.
- ⚠️ **Отступление от отправной точки ТЗ (Qwen2.5-14B Q4):** 14B Q4_K_M — это ~9 GB весов + ~0.7–1.3 GB KV-кэш + ~1 GB буферы ≈ 11 GB. Вместе с Whisper (~2–2.5 GB) и Zoom (он тоже ест VRAM на Windows, 0.5–1.5 GB на видеодекодинг) — это гарантированный вылет за 12 GB и частичная выгрузка слоёв на CPU → анализ растягивается на минуты. Подробный расчёт в §3.
- Консервативная альтернатива, если Qwen3 чем-то не устроит: `qwen2.5:7b-instruct-q4_K_M` — тот же бюджет памяти, чуть слабее.
- Держим модель загруженной постоянно (`keep_alive=-1`): всплеск раз в 4 минуты, перезагрузка стоила бы 5–15 с и сбрасывала бы кэш префикса.
- Контекст `num_ctx=8192` (обязательно задать явно — дефолт Ollama меньше). Бюджет запроса: системный промпт + схема ~1k ток. + гайд ~1–2k + состояние покрытия ~0.5–1k + дельта транскрипта за 4 мин ~1.5–2k ≈ 5–6k входа, до ~1.5k выхода.
- `format=<json-схема>` в Ollama принуждает декодер к валидному JSON — плюс pydantic-валидация и один повторный запрос при сбое.
- Порядок промпта фиксированный (системный промпт → гайд → состояние → дельта): статичный префикс попадает в кэш Ollama, и prefill на повторных циклах почти бесплатен.

## 3. Бюджет памяти

### Windows: RTX 4070 Super, 12 GB VRAM / 32 GB RAM

| Потребитель | VRAM |
|---|---|
| faster-whisper large-v3-turbo FP16 + CUDA/cuDNN контекст | ~2.0–2.5 GB |
| Qwen3-8B Q4_K_M (веса ~5.2 GB + KV 8k fp16 ~1.2 GB + буферы) | ~6.5–7.5 GB |
| Zoom (видеокодеки), WebView2/DWM | ~0.7–1.5 GB |
| **Итого** | **~9.5–11 GB** |

Влезает, но запас ~1–2 GB — поэтому лестница деградации (в конфиге, применяется по шагам):
1. KV-кэш q8_0 (`OLLAMA_KV_CACHE_TYPE=q8_0`, `OLLAMA_FLASH_ATTENTION=1`) → −0.6 GB.
2. Whisper `int8_float16` → −0.7 GB (качество почти не падает).
3. `num_ctx` 8192 → 6144.
4. LLM → `qwen3:4b-instruct-2507` (~2.6 GB) — на удивление сильная малютка, приемлемый русский.
5. Whisper на CPU — последний вариант ⚠️: large-v3-turbo int8 на CPU ~реальное время, два канала могут не успевать; тогда модель ASR ↓ до `medium`.

Приоритет при нехватке: **Whisper остаётся на GPU, ужимаем LLM** — транскрипция работает непрерывно, LLM — редкими всплесками и терпит задержку.

Почему не 14B: 11 GB (LLM) + 2.5 (Whisper) + 1 (Zoom/DWM) ≈ 14.5 GB > 12. Ollama выгрузит часть слоёв на CPU → генерация ~10–20 ток/с, цикл анализа 1.5–3 мин — впритык к 4-минутному интервалу.

RAM (32 GB): Python + буферы аудио + ONNX VAD < 2 GB, проблем нет.

### macOS: M4, 32 GB unified memory

| Потребитель | Память |
|---|---|
| mlx-whisper large-v3-turbo | ~1.5–2 GB |
| Qwen3-8B Q4 (Ollama) | ~6–7 GB |
| macOS + Zoom + окно приложения | ~6–9 GB |
| **Итого** | **~14–18 GB** — запас большой |

⚠️ Памяти на Mac хватает и на 14B (~10–11 GB), но «не ниже M4» включает **базовый M4 с пропускной способностью памяти 120 GB/s**: для 14B Q4 это ~10–13 ток/с генерации и медленный prefill → цикл анализа 2.5–3.5 мин, впритык. На 8B — ~20–25 ток/с, цикл ~60–90 с. Поэтому дефолт 8B и на Mac (бонус: одинаковое поведение промптов на обеих платформах). В конфиге — одна строка, чтобы поднять до `qwen3:14b` на M4 Pro/Max.

## 4. Поток данных

```
[Микрофон] ──callback──▶ RingBuffer A (INTERVIEWER) ─┐
                                                     ├─▶ VAD-чанкер (CPU): режет по паузам
[BlackHole/VB-Cable] ─▶ RingBuffer B (RESPONDENT) ───┘   ≥0.7 c, максимум 25 c
                                                              │  чанк + метка говорящего + t0/t1
                                                              ▼
                                               Очередь ASR ─▶ Whisper (1 экземпляр, GPU)
                                                              │  сегменты текста
                                                              ▼
                                                    TranscriptStore (память + append на диск)
                                                              │ событие "segment"
        ┌─────────────────────────────────────────────────────┤
        ▼                                                     ▼
  WebSocket-хаб ◀── next_analysis_at ── Планировщик (240 c / кнопка "Анализировать сейчас")
        │                                                     │ собирает: гайд + состояние + ДЕЛЬТА транскрипта
        ▼                                                     ▼
  UI 600×400 (pywebview)                        CoverageEngine ─▶ Ollama (127.0.0.1:11434)
                                                              │ JSON (format=schema, pydantic, 1 ретрай)
                                                              ▼
                                          слияние состояния + рекомендации ─▶ WS ─▶ UI
                                                              └─▶ SessionStore (диск)
```

Потоки/конкурентность:
- Callback'и PortAudio (свои потоки) только пишут в кольцевые буферы — никакой работы внутри callback.
- Один поток-чанкер на канал: гоняет VAD, отрезает чанк по паузе или по 25 с, кладёт в общую очередь ASR.
- Один ASR-воркер (thread executor) — сериализует доступ к GPU; сегменты упорядочиваются по времени начала чанка.
- FastAPI/WS — asyncio event loop; вызов Ollama — асинхронный HTTP (`httpx`), транскрипция продолжается параллельно с анализом (обе модели резидентны, см. бюджет).
- Таймер: сервер шлёт `next_analysis_at`, клиент сам рисует обратный отсчёт (без тиков по WS каждую секунду).

Задержки (ожидаемые): реплика появляется в транскрипте через ~3–30 с после произнесения (ждём паузу + транскрипция); цикл анализа — 15–40 с на Windows, 60–90 с на базовом M4. Для 4-минутного ритма достаточно.

## 5. Схемы JSON

### 5.1. Структурированный гайд (результат парсинга LLM, подтверждается пользователем)
```json
{
  "guide_id": "g-20260711-1430",
  "language": "ru",
  "title": "Исследование X",
  "sections": [
    {
      "id": "s1",
      "title": "Контекст использования",
      "topics": [
        {
          "id": "s1.t1",
          "question": "Как вы сейчас решаете задачу X?",
          "notes": "необязательное уточнение из гайда",
          "priority": "must"
        }
      ]
    }
  ]
}
```

### 5.2. Состояние покрытия (running state, живёт весь сеанс)
```json
{
  "session_id": "2026-07-11_14-30-00",
  "analysis_iteration": 3,
  "updated_at": "2026-07-11T14:42:07+03:00",
  "topics": {
    "s1.t1": {
      "status": "covered",          // covered | partial | not_covered
      "confidence": 0.9,
      "evidence": "краткий парафраз/цитата, чем тема закрыта",
      "last_update_iteration": 3
    }
  }
}
```

### 5.3. Ответ LLM на цикле анализа (строго по схеме, `format=json_schema`)
```json
{
  "topic_updates": [
    { "topic_id": "s1.t2", "status": "partial", "confidence": 0.7,
      "evidence": "респондент упомянул..., но не раскрыл..." }
  ],
  "recommendations": [
    {
      "type": "coverage_gap",
      "topic_id": "s1.t3",
      "urgency": "high",
      "note": "Тема не поднималась, интервью перевалило за середину",
      "suggested_question": "Расскажите, как вы поступаете, когда...?"
    }
  ]
}
```

Правила движка:
- LLM возвращает **только изменения** (`topic_updates`), движок сливает их в состояние.
- **Монотонность**: статус движется только вперёд (`not_covered → partial → covered`); понижение игнорируется — защита от «мигания» статусов между итерациями.
- Неизвестные `topic_id` отбрасываются и логируются.
- Невалидный JSON: срезка markdown-ограждений → повторный запрос с текстом ошибки (1 раз) → при повторном сбое итерация пропускается с записью в лог и статус-строкой в UI (данные не теряются — дельта войдёт в следующий цикл).
- **Расширяемость**: `type` рекомендации — открытый enum. MVP знает только `coverage_gap`; будущие пробинг-вопросы = новый `type: "probe"` (+ поле `quote` с репликой-триггером) → отдельный блок рендера во фронте, ядро не трогается.

### 5.4. Конверт WebSocket
```json
{ "type": "segment | coverage | recommendations | timer | status | error", "payload": { } }
```

## 6. Структура проекта

```
app/
  config.py          # всё в одном месте: устройства, модели, интервал (240 c), пути, лестница деградации
  main.py            # запуск: pywebview + uvicorn-поток; флаг --browser
  audio/capture.py   # перечисление устройств, 2 входных потока, кольцевые буферы
  audio/chunker.py   # Silero VAD, нарезка по паузам
  asr/base.py        # интерфейс ASRBackend.transcribe(chunk) -> Segment
  asr/mlx_backend.py / faster_backend.py   # + выбор по платформе, CPU-фолбэк
  transcript/store.py # сегменты, дельта-курсор для анализа, append на диск
  llm/ollama_client.py # health-check, structured output, ретраи, логирование обменов
  guide/parser.py    # текст гайда -> JSON (LLM) -> подтверждение пользователем
  coverage/engine.py # состояние, слияние, промпты, планировщик 240 c + ручной запуск
  server/app.py      # FastAPI: REST (устройства, гайд, старт/стоп) + WS-хаб
  storage/session.py # папка сессии, периодическое и финальное сохранение
  web/               # index.html + app.css + app.js (без сборки, без CDN)
sessions/            # результаты (в .gitignore)
requirements-common.txt / -macos.txt / -windows.txt
README.md
```

Персистентность (`sessions/2026-07-11_14-30-00/`): `transcript.jsonl` (append после каждого сегмента — живёт при сбое), `transcript.md`, `guide.json`, `coverage_state.json` (перезапись после каждого цикла), `recommendations.jsonl` (история), `analysis_log.jsonl` (сырые обмены с LLM для отладки), `meta.json`. Markdown-версия перегенерируется каждый цикл и финально на «Стоп».

UI 600×400: три вкладки — **Темы** (чеклист: ●/◐/○ + счётчик «7/12»), **Подсказки** (приоритет: high-gap сверху, готовые формулировки, кнопка «скопировать»), **Настройка** (устройства, гайд с подтверждением структуры, Старт/Стоп/Анализировать сейчас). Таймер и статус-строка — в постоянном хедере. Приоритет отдан вкладке «Подсказки» — она активна по умолчанию во время сессии.

## 7. Допущения

1. Zoom и приложение на одной машине; звук респондента маршрутизируется в BlackHole (через Multi-Output Device, чтобы пользователь слышал) / VB-Cable (на Windows — «прослушивать это устройство» на CABLE Output, либо Zoom сам дублирует вывод). Пошагово — в README.
2. Аудио **не сохраняется** на диск (только транскрипты) — приватность и место; флаг в конфиге, чтобы включить WAV для отладки.
3. Ollama установлена и запущена пользователем; при старте приложение проверяет сервер и наличие модели (`/api/tags`) и даёт понятную инструкцию, если нет.
4. Одна сессия за раз; гайд ~1–2 страницы (≤ ~40 тем). Более длинные гайды — вне MVP (потребуют анализ по частям).
5. Наушники у интервьюера (иначе голос респондента из колонок попадёт в микрофон и продублируется в канале INTERVIEWER — эхоподавление вне MVP).
6. Windows 10 22H2+/11 (WebView2 есть в 11), macOS 14+, Python 3.11+.
7. Первый запуск требует сети для скачивания весов (Whisper, Qwen) — данных интервью это не касается; дальше всё офлайн.

## 8. Явно спорные места (⚠️ — жду возражений, иначе делаю так)

1. **8B вместо 14B по умолчанию на обеих платформах** — из-за 12 GB на Windows и 120 GB/s на базовом M4 (§2–3). 14B — одна строка в конфиге.
2. Шум транскрипции при переключении языка внутри фразы — ограничение Whisper, принято ТЗ.
3. Появление текста с лагом до ~30 с (чанки по паузам) — цена отказа от streaming-ASR, на 4-минутный цикл не влияет.
4. pywebview на Windows требует WebView2 Runtime; фолбэк `--browser` теряет always-on-top (будет в README).
5. Кнопка «скопировать» у формулировок — маленькое дополнение к ТЗ, считаю полезным в 600×400.

## 10. План работ MVP (порядок модулей, каждый — проверяем отдельно)

1. **M0** — скелет: конфиг, логирование, structure, requirements.
2. **M1** — аудио: перечисление устройств, двухканальный захват, кольцевые буферы, VAD-чанкер; отладочная запись чанков в WAV.
3. **M2** — ASR: интерфейс + mlx/faster-бэкенды + CPU-фолбэк, TranscriptStore, живой транскрипт через WS. *Контрольная точка: смешанная RU/EN речь из Zoom транскрибируется в два канала.*
4. **M3** — LLM: клиент Ollama, health-check, парсер гайда + экран подтверждения структуры.
5. **M4** — движок покрытия: состояние, планировщик 240 с + ручной запуск, промпты, валидация/ретраи, рекомендации. *Контрольная точка: прогон записанного интервью файлом.*
6. **M5** — фронтенд 600×400 целиком + pywebview (always-on-top).
7. **M6** — персистентность сессий (append-по-ходу, финализация).
8. **M7** — README (BlackHole/VB-Cable/Zoom-маршрутизация, Ollama, установка на обеих ОС), полировка ошибок, чек-лист кросс-платформенного теста.
